# Applicant Notification Feature – Backend Implementation Guide

This document describes **how to implement the real-time Applicant Notification feature** using **Kafka**.

This feature is **event-driven**, **stateless**, and independent from manual applicant search.

---

## 1. Purpose

The notification feature ensures that:

- Every **new or updated applicant profile** is evaluated
- All **active premium search profiles** are checked
- Companies receive **immediate notifications** when a match occurs

> **Team Responsibility Note**
>
> In this project, the **actual Notification Service (delivery, UI updates, real-time push, etc.)** is implemented by **another member of the group**.
>
> Your responsibility in this service is limited to:
> - Defining and producing the **Kafka notification event (`company.notification`)**
> - Ensuring the event payload contains all required information
> - Providing stable event contracts that other team members can consume
>
> You do **NOT** need to implement:
> - Notification persistence
> - WebSocket / SSE delivery
> - Company-facing notification UI
>
> Those responsibilities are handled by the dedicated Notification Service.

---

## 2. Architectural Rule (Critical)

> **Do NOT cache applicant search results.**

Notifications are generated by:
- Evaluating **one applicant event**
- Against **all active saved search profiles**

There is no comparison with historical search results.

---

## 3. High-Level Flow

```
Applicant Service
   |
   |  applicant.profile.updated
   v
Kafka
   |
   v
Applicant Search Service
   |
   |  match against saved profiles
   v
Kafka: company.notification
```

### Topic

```
applicant.profile.updated
```

### Payload (subject to change)

```json
{
  "applicantId": "uuid",
  "countryCode": "VN",
  "highestDegree": "BACHELOR",
  "desiredSalary": 1400,
  "employmentTypes": ["FULL_TIME"],
  "skillIds": ["uuid-1", "uuid-2"]
```

## 5. Matching Algorithm (Rule-Based)

For each incoming applicant event:

1. Load all **active search profiles**
2. Skip profiles where company is **not premium**
3. Apply filters in order:
   - Country
   - Salary range
   - Employment type intersection
   - Education level
   - Skill intersection (OR)
4. If matched → generate notification

---

## 6. Notification Deduplication (Optional but Recommended)

To avoid repeated notifications for the same applicant:

- Store a Redis key:

```
notified:{companyId}:{profileId}:{applicantId}
```

- Set TTL (e.g. 24 hours or 7 days)
- If key exists → skip notification

This is optional and lightweight.

---

## 7. Produced Kafka Event

### Topic

```
company.notification
```

### Payload

```json
{
  "companyId": "uuid",
  "type": "APPLICANT_MATCH",
  "message": "A new applicant matches your saved search",
  "applicantId": "uuid"
}
```

---

## 8. What This Service MUST Store

- Saved search profiles
- Subscription cache (Redis)

## What This Service MUST NOT Store

- Applicant profiles
- Applicant history
- Search results

---

## 9. Failure Handling

| Scenario | Handling |
|------|---------|
| Kafka message failure | Retry / DLQ |
| Subscription cache miss | REST fallback |
| Notification failure | Retry or log |

---

## 10. Definition of Done

- Applicant updates trigger matching
- Premium validation enforced
- Notifications produced correctly
- No applicant data cached
